# AGENTS.md — LLM Intentions Android Hub

You are an LLM with access to the LLM Intentions Hub running on an Android device. This guide tells you how to use it well. Read this once before your first tool call.

## Connection

The Hub speaks MCP over streamable HTTP at:

```text
http://127.0.0.1:8379/mcp
```

The endpoint is loopback-only **and authenticated**. Every local HTTP request must include the bearer credential generated by the Hub app:

```http
Authorization: Bearer <device-local-token>
```

For CLI/developer setup, use the **Authenticated Local MCP Config** shown by the Hub dashboard. Do not guess, log, publish, or commit the token. The local token is not a future relay credential.

Do not expose port `8379` on Wi-Fi/LAN or the public Internet. Consumer remote access belongs behind the separate outbound authenticated relay architecture.

Tools are namespaced by CapApp:

| Namespace | CapApp | Capability |
|---|---|---|
| `hub.*` | Hub built-in | Discovery, status, Hub management |
| `taichi.*` | Taichi | Paper crypto trading, on-chain data, portfolio |
| `device.*` | tool-device | Sensors, TTS, vibration, clipboard on Android |
| `notify.*` | tool-notify | Notification read / post / reply, listener events |
| `people.*` | tool-people | Contacts and calendar capabilities |
| `files.*` / `fs.*` | file CapApps | Sandboxed / development filesystem capabilities |
| `termux.*` | optional termux-mcp | Termux APIs when that separate server is installed |

## Protocol compatibility

The Hub prefers MCP `2026-07-28` stateless semantics. Modern requests include the required per-request metadata and mirrored HTTP headers such as `MCP-Protocol-Version`, `Mcp-Method`, and, where applicable, `Mcp-Name`.

An initialize-era MCP `2025-06-18` compatibility path remains during migration. Authentication of the local HTTP endpoint applies to both eras.

## Return format

Every tool call can return a canonical envelope rendered as text:

```text
OK: <one-line summary>

<data JSON>
```

or:

```text
FAIL: <one-line summary>
Hint: <what to do next>

Raw:
<exception / stderr JSON>
```

**When you see `FAIL:`, read the `Hint:` line before retrying.** Hints map known failure patterns to concrete actions such as granting a permission, calling a prerequisite tool, or correcting an argument. If a hint is absent, the `Raw:` block is the next best clue.

A tool may also provide `structuredContent`; do not assume that all machine-readable results must be parsed back out of the text envelope.

## Permissions you cannot grant yourself

Android permissions for each CapApp are requested in-app by the user. If a tool returns FAIL with a permission hint, tell the user which permission is required — do not silently retry or attempt to bypass Android permission controls.

Examples:

| Permission | Typical CapApp / capability |
|---|---|
| `POST_NOTIFICATIONS` | notification posting |
| `BIND_NOTIFICATION_LISTENER_SERVICE` | notification reading/reply flows |
| `READ_CONTACTS`, `WRITE_CONTACTS` | contact tools |
| `READ_CALENDAR`, `WRITE_CALENDAR` | calendar tools |
| `MANAGE_EXTERNAL_STORAGE` | development filesystem CapApp |
| location / camera / microphone | only CapApps that explicitly expose those device capabilities |

## Destructive or externally visible tools

Tools that modify device/user-visible state, send communications, delete data, or produce physical/audible output should not be called speculatively. Respect the user's expressed intent and the tool's annotations/policy metadata.

Examples include:

- `taichi.paper_trade`, `taichi.paper_reset`;
- notification post/reply/dismiss actions;
- contact or calendar writes/deletes;
- filesystem writes/deletes;
- TTS, vibration, or other visible/audible device actions.

The Hub policy/consent layer is being expanded. Tool annotations are advisory context, not a substitute for authorization.

## Latency classes

- `FAST` — generally sub-second local work.
- `SLOW` — seconds: network calls, larger queries, shell/integration work.
- `VERY_SLOW` — may exceed normal interactive latency.

Do not assume failure merely because a tool belongs to a slower class; honor the transport/tool timeout semantics.

## Common sequences

### "Buy some ETH with $100"
1. Use the appropriate Taichi lookup/search capability to resolve the token.
2. Confirm that the user's intent to mutate the paper portfolio is unambiguous.
3. Invoke the paper-trade capability with the validated arguments.
4. Read the portfolio to verify the resulting state.

### "What's on my calendar?"
1. Use the available read-only calendar capability.
2. If it fails on permission, tell the user which Calendar permission to grant.

### "Send a reminder"
1. Use the available notification-post capability.
2. Do not repeatedly retry a permission failure; surface the required user action.

## Parameter conventions

- Respect every JSON Schema enum and type exactly.
- Numeric inputs are JSON numbers unless the schema says otherwise.
- Follow each tool's documented timestamp/file conventions rather than inventing coercions.
- Use returned IDs/handles when a later tool expects them.

## When a tool isn't enough

The Hub is curated. If no CapApp exposes the required Android capability, tell the user. Do not use an unrelated generic tool to smuggle around the capability boundary.

A new capability should normally become a CapApp or a deliberately reviewed Hub capability.

## Tools you probably shouldn't call unprompted

- communications or contact/calendar mutation tools;
- delete/reset operations;
- capabilities that consume a metered model/API budget;
- anything marked destructive or requiring explicit confirmation by policy.

## For CapApp authors

### Local IPC trust

CapApp Protocol v1 uses authenticated Binder IPC. Discovery metadata is not authorization. A CapApp must authenticate the Hub caller on every Binder transaction before performing privileged work.

Do not add a new privileged CapApp that exposes only the legacy `EXECUTE` / `LIST_TOOLS` started-service protocol. The v0 path exists for migration of already-deployed APKs, not as the trust model for new CapApps.

See [`spec/capapp-protocol.md`](spec/capapp-protocol.md) for the v1 contract and migration rules.

### 1. Throw on hard errors. Don't catch-and-return-error-string.

**Wrong** — the framework may interpret the returned string as success:

```kotlin
registry.textTool("my_tool", "...", params) { args ->
    try {
        doWork(args)
    } catch (e: Exception) {
        "Error: ${e.message}"
    }
}
```

**Right** — let the framework see the exception:

```kotlin
registry.textTool(
    name = "my_tool",
    description = "...",
    params = jsonSchema { /* ... */ },
    metadata = toolMetadata {
        failureMode(
            pattern = "sensor unavailable",
            hint = "This sensor isn't on this device — check the relevant capability first.",
        )
    },
) { args ->
    doWork(args)
}
```

The framework can then produce `FAIL: my_tool failed: ...` and attach an actionable hint.

If the tool intentionally needs to produce a `WARN` or a specific structured `FAIL` without throwing, use `envelopeTool` and return `Envelope.warn(...)` / `Envelope.fail(...)` directly.

### 2. Ship metadata with tools that can fail or mutate state.

`toolMetadata { failureMode(pattern = "...", hint = "...") }` turns opaque failures into recovery guidance. Also declare destructive/idempotent semantics accurately so standard MCP annotations and the future Hub policy engine have useful information.

Do not infer "read-only" merely from "not destructive": a non-destructive tool can still mutate state. The richer H2 descriptor/policy metadata will make this distinction explicit.
